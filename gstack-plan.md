## Problem Statement

Build a disaster rescue robot demo for a hackathon (deadline: 5PM PST today). A robot
navigates a simulated disaster environment (MuJoCo) to reach survivors. Gemini accepts
natural language commands ("save the child first") and translates them into a target
survivor the RL-trained robot then navigates to. Multi-survivor prioritization is the
demo centerpiece.

## What Makes This Cool

You say a sentence. A robot moves. That's the moment.

The multi-survivor setup makes it more than a party trick — judges see the robot
choosing between two people and can immediately understand why. "Go to the child" is
legible to anyone in the room, technical or not. The Gemini layer means judges see
language grounding a physical agent in real time. That's the state of the art, compressed
into 5 minutes.

## Premises

2. **FastAPI calls Gemini directly**; antigravity is used only to inject the goal coordinate into the running env (not as a Gemini wrapper)

## Approaches Considered

### Approach A: Gemini as Goal Selector (CHOSEN)
  Summary: Gemini takes NL command, returns target survivor ID/coordinates, RL policy navigates there.
  Effort:  S (2-3 hours per track, parallel)
  Risk:    Low
  Pros:    Fastest path to working demo; clean architecture; zero tool-call surface to break
  Cons:    Gemini does NLP, not reasoning — judges see selection, not deliberation
  Reuses:  antigravity bridge for JSON output

### Approach B: Gemini with Tool Calls + Environment Queries
  Summary: Gemini gets tools (get_env_state, set_target) and reasons before deciding.
  Effort:  M (3-4 hours, riskier under time pressure)
  Risk:    Medium
  Pros:    More impressive; Gemini explains its choice aloud
  Cons:    Extra integration surface; debugging tool calling under deadline is painful

## Recommended Approach

**Approach A: Gemini as Goal Selector**

Rationale: You have 6 hours and need a working demo, not a perfect one. Approach A
gives you a high probability of shipping something that runs cleanly in front of judges.
Gemini-as-goal-selector is still impressive — "say it and the robot moves" is the
headline. If you finish early, you can add Gemini's reasoning text to the UI (a text
box showing what Gemini said) without changing the architecture.

### Architecture

```
User types command in browser
        ↓
FastAPI POST /command (server.py)
        ↓
Gemini API (flash model, response_mime_type="application/json")
  response_schema: {target_id: enum["child","adult"], confidence: float, reason: str}
  fallback: if parse fails → default to "child" (never hard-crash the demo)
        ↓
Put target_coords onto multiprocessing.Queue
        ↓
robot_process.py picks up goal → env.set_goal(target_coords)
        ↓
PPO policy runs (env loop, 150 steps max)
  success: {reached: true, steps: N, reason: gemini_reason, target_id: "child"}
  timeout: {reached: false, steps: 150, reason: "timeout", target_id: "child"}
        ↓
Result written to shared Manager dict
        ↓
FastAPI reads result, returns JSON to browser
        ↓
MuJoCo viewer shows robot moving (second screen)
```

### DisasterEnv Design

File: `envs/disaster_env.py`
Class: `class DisasterEnv(gym.Env):`
Verify MuJoCo works first: `python -c "import mujoco; print(mujoco.__version__)"`
Starting point: extend MuJoCo `point_mass.xml` or `ant.xml`; add two fixed site bodies named `survivor_child` and `survivor_adult`.

Observation space (**10D base**):
- Robot XY position (2)
- Robot velocity (2)
- Survivor 1 (child) XY relative to robot (2)
- Survivor 2 (adult) XY relative to robot (2)
- Active target: 0=child, 1=adult (1)
- Distance to active target (1)

If time allows, expand to 12D by adding debris positions as 2 fixed zeros.

Action space: continuous 2D force (same as point_mass)

Reward: `-distance_to_active_target` per step + `100` on reach (`distance < 0.5`)

Episode timeout: 150 steps. If not reached: `{reached: false, steps: 150, reason: "timeout"}`

Survivors: 2 fixed positions at init, e.g. child at `(3.2, -1.5)`, adult at `(-2.1, 4.3)`.
Labels are metadata passed to Gemini only — the env uses coordinates, not names.

**Required method — `env.set_goal(target_id: str) -> None`:**
Track 1 must implement this. It updates the active target in the env so the PPO policy
navigates to the right survivor:
```python
def set_goal(self, target_id: str):
    # target_id is "child" or "adult"
    self.active_target = self.survivor_positions[target_id]
    self.active_target_id = target_id
```
`robot_process.py` calls this on receiving a goal from the Queue. Without it, Track 4 stalls.

**Survivors dict schema (shared contract between Track 1, 2, and 3):**
```python
SURVIVORS = {
    "child": (3.2, -1.5),
    "adult": (-2.1, 4.3),
}
```
Track 2's `get_gemini_target(command: str, survivors: dict) -> dict` receives exactly this.
Track 3 passes exactly this when calling `get_gemini_target`.

**Start training the moment `env.reset()` + `env.step(env.action_space.sample())` run without error.** Don't wait for the full env to be "done."

**Training fallback:** If 50k steps doesn't produce a navigating policy (reward isn't improving by 20k steps), fall back to a hardcoded rule-based policy: move toward `active_target` coordinates using proportional control (`action = k * (target - robot_pos)`, clipped to action bounds). This won't look elegant but the demo still shows the robot moving toward the right target.

### Process Architecture (CRITICAL on macOS)

MuJoCo's viewer requires the main thread on macOS. FastAPI/uvicorn runs its own event loop. **Do not run both in the same process — it will deadlock on Apple Silicon.**

Split into two processes:
- `robot_process.py` — runs the env loop + MuJoCo viewer (`mujoco.viewer.launch_passive`), listens on a `multiprocessing.Queue` for goal updates, writes episode results to a shared dict
- `server.py` — FastAPI + uvicorn, calls Gemini, puts goal onto the Queue, reads results

Communication: `multiprocessing.Manager().dict()` and `multiprocessing.Queue()`

Track 4 owns `run_demo.py` which spawns both processes:
```python
# run_demo.py
from multiprocessing import Process, Queue, Manager
# spawn robot_process, spawn uvicorn server, wire queue
```

### Training Run Data Pipeline (post-hackathon / parallel to demo)

Each `train.py` run should produce **machine-readable artifacts** so future agents and training jobs can compare runs, warm-start policies, and build offline datasets — not just a final `.zip` in `./models/`.

**Run layout** (per invocation):
```
runs/<run_id>/
  manifest.json      # hyperparams, git sha, env schema (obs/action dims), scene set hash
  checkpoints/       # PPO checkpoints from this run
  tb/                # TensorBoard logs scoped to this run
  eval_results.json  # per-scene reach/steps/reward from rescue_runner --suite
  trajectories/      # optional: exported (obs, action, reward) rollouts for IL / offline RL
```

**Why:** Without manifests, checkpoints from the 3D-action run vs grounded-2D run are indistinguishable blobs. Future runs (human or agent) need to know *which env version* produced *which data* before retraining or fine-tuning.

**Stretch (after demo):**
- `train.py --run-name <slug>` auto-creates run folder + manifest
- `rescue_runner.py --suite --run-id <run_id>` appends eval results to that run's ledger
- `scripts/compare_runs.py` diff eval + manifest across runs
- Export top trajectories from successful episodes as a reusable dataset
